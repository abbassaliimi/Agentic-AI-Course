Module 00: Preliminary Environment Setup

Module Overview: Why Environment Isolation Matters

Agentic applications sit at the intersection of application code (Python orchestration), external network APIs (LLMs and messaging webhooks), and stateful infrastructure (databases). Before writing agent logic, we establish two clean boundaries on your workstation:

  • Application Runtime Isolation (Python + Virtual Environments): Keeps project dependencies (such as specific versions of langgraph and psycopg) decoupled from your operating system's global Python installation.
  • Infrastructure Isolation (Docker Containers): Runs PostgreSQL inside a lightweight, disposable Linux container so you never have to manually configure OS-level database services, system users, or background daemons.

Module 0: Theoretical Foundations of Agentic Systems

0.1 From Passive Chatbots to Autonomous Agentic Systems

A common misconception is that an "AI Agent" is simply a chatbot with a longer system prompt. In reality, traditional LLM integrations and agentic systems differ fundamentally in who controls the execution flow:

Paradigm Control Flow State & Memory Failure Handling
1. Standard LLM Wrapper
(Single-Turn Completion)		 Linear: Prompt → LLM → Response. Zero branching or external actions. Stateless. Relies solely on static knowledge baked into model weights. Hallucinates when asked about private, real-time, or tabular data.
2. Deterministic Chain / RAG
(Fixed Pipeline)		 Hardcoded DAG (Directed Acyclic Graph): Retrieve → Stuff Prompt → Generate. Developer dictates every step. Read-only context injection per request; no iterative refinement. If initial retrieval misses the mark, the final answer fails silently.
3. Stateful Agentic System
(Cyclic Graph / ReAct)		 Dynamic & Cyclic: The LLM inspects state, chooses tools, observes outputs, and loops until done. Persistent Checkpoints: Full conversation + tool trace saved per user thread in PostgreSQL. Self-Correcting: Reads tool error messages, rewrites inputs, and retries autonomously.

0.2 Anatomy of the ReAct (Reason + Act) Paradigm

Modern tool-using agents operate on the ReAct (Reason + Act) framework. Rather than forcing the LLM to guess an answer in a single forward pass, we place the LLM inside a feedback loop where it can interact with deterministic software tools (databases, calculators, APIs) and observe real outcomes:

  1. State Ingestion (Context Assembly): The orchestrator loads the user's message alongside prior conversation turns and any previous tool outputs from the state store.
  2. Reasoning (Intent & Gap Analysis): The LLM evaluates whether it already possesses enough verified information to answer the user. If not, it determines which external tool can bridge the knowledge gap.
  3. Action Emission (Structured Tool Call): Instead of generating conversational prose, the LLM outputs a structured JSON payload specifying the target function name and arguments (e.g., execute_sql(query="SELECT SUM(revenue) FROM sales...")).
  4. Tool Execution & Observation: The Python runtime intercepts the tool call, executes the real code against external systems, and appends the raw output (or exception stack trace) back into the state as a ToolMessage.
  5. Iterative Evaluation & Termination: Control returns to the LLM. It inspects the new observation. If more data is needed—or if a query failed and needs fixing—it loops back to Step 3. Once satisfied, it synthesizes a natural-language response and exits the loop.

0.3 Core Architectural Pillars of Our Stack

1. Cyclic State Graph (LangGraph)

Standard DAG tools (like Airflow) forbid cycles. Agents require cycles because you cannot know in advance whether a task takes 1 tool call or 5 self-correction steps. LangGraph models the agent as a state machine of Nodes (functions) and Conditional Edges (routing decisions).

2. Checkpointed Persistence (Postgres)

LLMs are stateless mathematical functions: every API call starts from zero. LangGraph's Checkpointer serializes the entire graph state after every single node execution into PostgreSQL, keyed by a unique thread_id. This provides crash recovery and isolated multi-user memory.

3. Async Event Gateway (Telegram)

Real-world agents live inside messaging interfaces, not terminals. Using an asynchronous bot gateway allows our server to handle multiple users concurrently without blocking while waiting 1–3 seconds for LLM inference or SQL queries to complete.

0.5 End-to-End Request Lifecycle (Tracing a Single Message)

To solidify how these components collaborate, trace what happens the exact millisecond a user sends "What was Alice's total revenue?" on Telegram:

  1. Ingress & Identity Extraction: The Telegram Poller receives an HTTP JSON update containing the message text and the sender's unique numeric user_id (e.g., 987654321).
  2. State Hydration: Python invokes app.invoke(..., config={"configurable": {"thread_id": "987654321"}}). LangGraph queries PostgreSQL for the latest checkpoint matching thread 987654321, restoring full historical context before appending the new user message.
  3. Reasoning Step (Node 1 → LLM): The LangGraph Orchestrator sends the updated message list plus tool schemas to the LLM. Recognizing it cannot see the database directly, the LLM returns an AIMessage containing a tool_call for execute_sql.
  4. Conditional Routing & Execution (Node 2 → Tools): LangGraph's conditional edge detects the pending tool_call and routes execution to the Tools Node. Python runs the SQL query against Postgres, gets 250.75, saves a checkpoint, and routes back to the LLM.
  5. Final Synthesis & Checkpoint Commit: The LLM reads the ToolMessage (250.75), determines no further tools are needed, and emits a final plain-text AIMessage. LangGraph commits the final state checkpoint to PostgreSQL and returns control to Telegram.
  6. Egress Delivery: The Telegram handler extracts the final string and delivers it back to the user's chat screen.
Transition: Now that we understand the theoretical loop and data flow, we need to lay down the infrastructure. For our agent to possess true long-term memory across sessions, we first need a robust database to act as its hippocampus. Let's set up the environment.

Module 1: Environment & Database Setup

Theory: Local State Persistence with Postgres

Memory in LangGraph requires a persistent store to save the serialized state of the graph at every step (called Supersteps). While an in-memory dictionary (MemorySaver) wipes everything the moment your script restarts, and SQLite suffers from file-locking errors under concurrent async writes, PostgreSQL provides ACID-compliant, row-level concurrency out of the box.

By running PostgreSQL inside Docker, we get a production-grade relational database engine running locally on port 5432 that we can inspect, reset, or migrate cleanly.

Step 1.1: Spin up PostgreSQL via Docker

Ensure Docker Desktop is running, then execute this in your terminal to create and start a database container:

docker run --name agent-postgres \
  -e POSTGRES_USER=agent_user \
  -e POSTGRES_PASSWORD=agent_pass \
  -e POSTGRES_DB=agent_db \
  -p 5432:5432 \
  -d postgres:15

What Each Docker Flag Does

  • --name agent-postgres: Assigns a human-readable identifier so you can easily stop/start the container later (e.g., docker stop agent-postgres).
  • -e POSTGRES_USER / PASSWORD / DB: Injects environment variables into the container at boot time to automatically create our database user, password, and default schema.
  • -p 5432:5432: Maps port 5432 on your host laptop (left) to port 5432 inside the isolated container (right).
  • -d postgres:15: Runs the official PostgreSQL 15 image in detached mode (in the background) so your terminal remains free.

Module 2: Defining the ReAct Graph

Theory: Graph-Based Control Flow & State Reducers

In standard scripts, functions run sequentially from top to bottom. In LangGraph, we model our agent as a state machine governed by three core primitives:

  • State (AgentState): A shared typed dictionary passed to every node. By annotating messages with the add_messages reducer, whenever a node returns {"messages": [new_msg]}, LangGraph appends it to the conversation history rather than overwriting prior messages.
  • Nodes (agent, tools): Standard Python functions that read the current state, perform work (calling an LLM or running a tool), and return a partial state update.
  • Conditional Edges: Decision functions that inspect the state after a node finishes and dynamically route execution—either looping into the tools node if tool calls are requested, or terminating at END.

Step 2.1: Build the State Machine

Create a file named agent.py to define the skeleton of your graph and verify database checkpoint creation:

import os
from typing import TypedDict, Annotated
from psycopg_pool import ConnectionPool
from langgraph.graph import StateGraph, END
from langgraph.checkpoint.postgres import PostgresSaver
from langgraph.graph.message import add_messages
from dotenv import load_dotenv

load_dotenv()
DB_URI = os.getenv("DB_URI")

# 1. Define State
class AgentState(TypedDict):
    messages: Annotated[list, add_messages]

# 2. Mock Nodes (We'll expand these later)
def call_model(state: AgentState):
    return {"messages": [{"role": "assistant", "content": "I am alive."}]}

def execute_tools(state: AgentState):
    pass

def should_continue(state: AgentState):
    return "end" # Mock routing

# 3. Define Graph
workflow = StateGraph(AgentState)
workflow.add_node("agent", call_model)
workflow.add_node("tools", execute_tools)
workflow.set_entry_point("agent")
workflow.add_conditional_edges("agent", should_continue, {"continue": "tools", "end": END})
workflow.add_edge("tools", "agent")

# 4. Setup DB Checkpointer and Compile
pool = ConnectionPool(conninfo=DB_URI, max_size=20)
checkpointer = PostgresSaver(pool)
checkpointer.setup() # CRITICAL: Creates tables in DB if they don't exist

app = workflow.compile(checkpointer=checkpointer)

Code Walkthrough: Inside agent.py

  • Section 1 (State Schema): Annotated[list, add_messages] tells LangGraph how to merge state updates. Without add_messages, every new reply would erase previous turns.
  • Section 2 (Nodes & Router): We stub out call_model and execute_tools first so we can validate our graph wiring and Postgres integration independently before introducing LLM latency or API costs.
  • Section 3 (Topology Wiring): Notice workflow.add_edge("tools", "agent"). This creates the ReAct cycle—after tools execute, control always returns to the LLM so it can interpret the tool's output.
  • Section 4 (Connection Pool & Migration): ConnectionPool(max_size=20) maintains reusable TCP connections to PostgreSQL so concurrent Telegram users don't pay connection-handshake overhead. checkpointer.setup() automatically executes SQL DDL migrations to create the checkpoint tables on first startup.

Module 3: Exposing via Telegram Async Bot

Theory: Stateful Conversations on Stateless Platforms

Messaging platforms like Telegram deliver every incoming chat message as an independent, stateless event. To transform isolated messages into a continuous, multi-turn conversation—while keeping different users completely isolated—we bridge Telegram's user identity to LangGraph's checkpointing system:

  • Thread Isolation (thread_id): By extracting update.effective_user.id and passing it as thread_id inside the graph's config dictionary, PostgreSQL partitions conversation histories per user automatically. User A's queries never bleed into User B's context window.
  • Long-Polling vs. Webhooks: In production, bots often use HTTPS Webhooks. During local development, Long-Polling (run_polling()) allows your local Python process to open an outbound connection to Telegram's servers and pull new messages immediately—requiring zero public IP addresses, SSL certificates, or tunneling tools like ngrok.
  • Asynchronous Execution (async/await): Using non-blocking coroutines ensures network I/O (sending Telegram replies) yields control cleanly on the event loop.

Step 3.1: Long-Polling Binding

Create a file named bot.py to connect Telegram events to your compiled LangGraph app:

from telegram import Update
from telegram.ext import ApplicationBuilder, MessageHandler, filters, ContextTypes
from agent import app # Import the compiled graph from Module 2
import os
from dotenv import load_dotenv

load_dotenv()

async def handle_message(update: Update, context: ContextTypes.DEFAULT_TYPE):
    user_id = update.effective_user.id
    user_input = update.message.text
    
    print(f"Received message from {user_id}: {user_input}")
    
    # Pass user_id as thread_id for persistent state memory isolation
    config = {"configurable": {"thread_id": str(user_id)}}
    
    # Invoke the graph
    response = app.invoke({"messages": [("user", user_input)]}, config)
    
    # Reply to user
    final_message = response["messages"][-1]["content"] if isinstance(response["messages"][-1], dict) else response["messages"][-1].content
    await update.message.reply_text(final_message)

if __name__ == '__main__':
    bot_app = ApplicationBuilder().token(os.environ["TELEGRAM_BOT_TOKEN"]).build()
    bot_app.add_handler(MessageHandler(filters.TEXT, handle_message))
    print("Bot is polling... Waiting for messages from Telegram.")
    bot_app.run_polling()

Code Walkthrough: Inside bot.py

  • filters.TEXT: Ensures our handler only triggers on text messages (ignoring stickers, photos, or voice notes unless explicitly handled).
  • config = {"configurable": {"thread_id": str(user_id)}}: The critical binding key. LangGraph uses this string to look up existing rows in the Postgres checkpoints table before running the graph, and saves the updated message list back under this ID afterward.
  • response["messages"][-1]: Because AgentState appends every message in chronological order (User → AI Tool Call → Tool Output → Final AI Answer), index -1 always holds the agent's final synthesized response.

Module 4: Data Science Use Case: Text-to-SQL EDA Agent

Theory: Agentic SQL Execution & Autonomous Self-Correction

Standard vector-based RAG (Retrieval-Augmented Generation) struggles with structured tabular data—chunking rows into embeddings destroys mathematical relationships, making aggregations like SUM, AVG, or GROUP BY unreliable.

Instead, we give the LLM direct access to a deterministic execute_sql tool and leverage three agentic principles:

  • Docstrings as Tool Schemas: The @tool decorator inspects your Python function signature and docstring to generate a JSON Schema sent to the LLM. Describing the exact table name (sales) and column types inside the docstring grounds the LLM so it writes accurate queries on the first try.
  • Closed-Loop Error Recovery: If the LLM hallucinates a column name or writes invalid PostgreSQL syntax, our try/except block catches the database exception and returns the error message as a string observation rather than crashing the Python process. On the next loop iteration, the LLM reads the Postgres error, diagnoses its mistake, and writes a corrected query autonomously.
  • High-Level Graph Compilation (create_react_agent): Once you understand how nodes, conditional edges, and state reducers work under the hood (Module 2), LangGraph's prebuilt create_react_agent compiles that exact ReAct topology in a single line while preserving full compatibility with our PostgreSQL checkpointer.

Step 4.1: Seed Dummy Data & Create the SQL Tool

Replace the contents of agent.py to seed a sample sales table in PostgreSQL, bind the execute_sql tool, and initialize the Llama-3 70B reasoning model:

import os
from psycopg_pool import ConnectionPool
from langgraph.checkpoint.postgres import PostgresSaver
from langchain_core.tools import tool
from langchain_groq import ChatGroq
from langgraph.prebuilt import create_react_agent
import pandas as pd
from sqlalchemy import create_engine
from dotenv import load_dotenv

load_dotenv()
DB_URI = os.getenv("DB_URI")
engine = create_engine(DB_URI)

# 0. Initialize PostgreSQL Checkpointer (Persisted from Module 2)
pool = ConnectionPool(conninfo=DB_URI, max_size=20)
checkpointer = PostgresSaver(pool)
checkpointer.setup()

# 1. Seed Dummy Data (Run once on startup)
df = pd.DataFrame({
    "product": ["Widget A", "Widget B", "Widget A", "Widget C"], 
    "revenue": [100.50, 200.00, 150.25, 300.75],
    "sales_rep": ["Alice", "Bob", "Alice", "Charlie"]
})
df.to_sql("sales", engine, if_exists="replace", index=False)

# 2. Define the Tool
@tool
def execute_sql(query: str) -> str:
    """Executes a SQL query on the PostgreSQL database. 
    The database has a table called 'sales' with columns: product (TEXT), revenue (FLOAT), sales_rep (TEXT)."""
    print(f"[TOOL EXECUTION] Running SQL: {query}")
    try:
        result = pd.read_sql(query, engine)
        return result.to_markdown()
    except Exception as e:
        return f"Error executing query: {str(e)}. Please rewrite the query and try again."

# 3. Initialize the Real LLM
llm = ChatGroq(model="llama3-70b-8192")
tools = [execute_sql]

# 4. Use the pre-built ReAct Agent constructor (replaces manual graph routing)
app = create_react_agent(llm, tools, checkpointer=checkpointer)

Code Walkthrough & Production Considerations

  • Markdown Table Formatting (result.to_markdown()): LLMs parse Markdown tables significantly more cleanly than raw Python tuples or unformatted DataFrame strings, reducing arithmetic interpretation errors.
  • Multi-Turn Memory in Action: Because checkpointer=checkpointer is attached to create_react_agent, you can ask follow-up questions on Telegram (e.g., "Who sold the most?" followed by "What products did they sell?") and the agent will resolve "they" from its PostgreSQL thread history.
  • Production Security Note: In production deployments, always connect Text-to-SQL agents using a restricted read-only PostgreSQL role (GRANT SELECT ON ...) so prompt injection cannot execute DROP TABLE or DELETE statements.
